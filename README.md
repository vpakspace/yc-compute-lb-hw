|---|---|---|
| VPC `netology-vpc`, подсеть `public` 192.168.10.0/24, группа безопасности `lamp-web-sg` | [network.tf](terraform/network.tf) | та же сеть, что в предыдущем ДЗ блока 15; SG пускает только 80/tcp, SSH не открыт |
| SA `ig-sa` (5 ролей) и `storage-sa` (`storage.editor`) + статический ключ | [iam.tf](terraform/iam.tf) | `ig-sa` — от его имени группа ВМ создаёт ВМ и target group; ключ `storage-sa` нужен для загрузки объекта |
| Бакет `vpakspace-20261125` и объект `picture.png` | [storage.tf](terraform/storage.tf) | картинка читается анонимно, список объектов закрыт |
| `yandex_compute_instance_group.lamp` | [instance_group.tf](terraform/instance_group.tf) | 3 ВМ LAMP, `user_data`, health check, подключение к балансировщику |
| NLB `lamp-nlb` | [nlb.tf](terraform/nlb.tf) | L4-балансировщик, проверка HTTP GET / |
| ALB `lamp-alb`, роутер, виртуальный хост, backend group | [alb.tf](terraform/alb.tf) | L7-балансировщик (дополнительная часть) |

ВМ: `standard-v3`, 2 vCPU с гарантированной долей 20 %, 2 ГиБ RAM, загрузочный HDD 5 ГиБ (образ LAMP требует ≥ 3 ГиБ).
Параметры подобраны под квоты моего облака: в зоне ru-central1-a 2 «эффективных» ядра (3 ВМ × 2 vCPU × 20 % = 1,2) и 20 ГиБ HDD.

**Режимы `balancer`.** Группа ВМ подключается только к одному балансировщику одновременно: API отвечает
`Only one of (load_balancer_spec, application_load_balancer_spec) can be specified` ([подробности](#находки-и-ошибки-по-пути)).
Поэтому в коде есть переменная `balancer = "nlb" | "alb"` (по умолчанию `nlb`, основная часть задания): она включает нужный блок
группы через `dynamic`, а оба балансировщика остаются созданными. Смена режима пересоздаёт группу.

## Как запустить

```bash
cd terraform
cp personal.auto.tfvars_example personal.auto.tfvars        # подставить cloud_id и folder_id
export TF_CLI_CONFIG_FILE=$PWD/.terraformrc                 # зеркало провайдеров

# SA terraform имеет только editor и не может назначать роли. На время apply владелец облака выдаёт ему admin:
yc resource-manager folder add-access-binding <folder_id> --role admin --service-account-id <id SA terraform>
terraform init && terraform apply                           # режим nlb (по умолчанию)
yc resource-manager folder remove-access-binding <folder_id> --role admin --service-account-id <id SA terraform>

../scripts/check.sh nlb          # логи 03–05: бакет, группа, балансировщик
../scripts/failover.sh nlb       # лог 06: удаляем две ВМ под нагрузкой

terraform apply -var balancer=alb      # группа пересоздаётся и подключается к ALB (роли уже назначены первым apply, admin не нужен)
../scripts/check.sh alb && ../scripts/failover.sh alb
```

Бакет создаётся от имени провайдера (IAM-токен SA `terraform`), а объект в него пишется статическим ключом `storage-sa`
с ролью `storage.editor`: запись объектов идёт через S3 API. Публичность задаётся флагом бакета, а не ACL объекта:

```hcl
resource "yandex_storage_bucket" "this" {

    list = false   # список объектов анонимам закрыт

  force_destroy = true
}
```

### 2. Группа ВМ с шаблоном LAMP

[`instance_group.tf`](terraform/instance_group.tf): `fixed_scale` на 3 ВМ в публичной подсети, у каждой ВМ публичный IP (`nat = true`),
имена `lamp-1…3` строятся по шаблону `lamp-{instance.index}`. Стартовая страница создаётся в разделе `user-data`
([шаблон](terraform/files/user-data.sh.tftpl)); ссылка на картинку подставляется из реального адреса объекта, а имя ВМ берётся на самой машине
(`hostname`), иначе по ответам нельзя было бы понять, какая ВМ ответила:

```bash
HOST=$(hostname)
cat > /var/www/html/index.html <<EOF
...
  <h2>Отвечает ВМ: $HOST</h2>
  <p><a href="${picture_url}">${picture_url}</a></p>
  <img src="${picture_url}" alt="Картинка из бакета" width="800">
...
EOF
```

и пересоздаётся. Отдельно есть проверка у балансировщика (шаги 3 и 5): она лишь выводит цель из ротации.

### 4. Проверка: удаляем ВМ

[`scripts/failover.sh nlb`](scripts/failover.sh): в фоне на адрес NLB идёт по одному запросу в секунду; удаляем `lamp-1`, через ~20 с `lamp-2`
(остаётся одна ВМ), затем ждём, пока группа сама вернёт размер. Весь ход — в одном логе с метками времени ([06_failover_nlb.log](logs/06_failover_nlb.log)).

![NLB: удаление ВМ под нагрузкой](img/06_failover_nlb_1.png)
![NLB: восстановление группы и сводка](img/06_failover_nlb_2.png)

Что видно в логе:

- **Сервис не прерывался.** 113 запросов: 109 вернули 200, 4 оборвались. Из 109 ответов 83 дала `lamp-3`, она одна пережила оба удаления; `lamp-1` и `lamp-2` ответили 12 и 14 раз: только в начале теста и после возвращения.
- **Обрывы — это окно обнаружения отказа.** Все 4 — таймауты по ровно 1,0 с (`--connect-timeout 1`), по два на каждое удаление: через 10–14 с после команды `delete`.
  NLB работает на L4 и не терминирует соединение: пока цель не признана нездоровой (2 проверки × 2 с), пакеты на неё просто пропадают.
- **Группа вернула ВМ сама**: через 2 мин 45 с после первого удаления снова `RUNNING=3`, `HEALTHY=3`, и в ротацию вернулись новые `lamp-1` и `lamp-2`.
- Одна пауза самого измерителя (12 с, помечена в логе) не совпала ни с одним обрывом. Про такие паузы подробнее в [находках](#находки-и-ошибки-по-пути).

Оговорка про точность: это один прогон по одному запросу в секунду, поэтому «по два обрыва на удаление» — наблюдение, а не статистика. В первом прогоне
(лог перезаписан при исправлении скрипта) было то же самое: по два обрыва на удаление; во втором их скрыли паузы измерителя, а текущий прогон — третий.

## Находки и ошибки по пути

**1. Группе ВМ с `nat = true` нужна роль `vpc.publicAdmin`. Это стоило 30 минут.** С ролями `compute.editor`, `vpc.user`, `load-balancer.editor` группа каждые 5 минут
создавала три ВМ и тут же удаляла их, а `terraform apply` висел на группе. Причину показывает только журнал группы, а не Terraform:

```text
$ yc compute instance-group list-instances --name lamp-group      (сокращённо: таблица в терминале длиннее)
 lamp-1 … DELETED [5m]  [PERMISSION_DENIED] Permission denied to resource-manager.folder b1gabvo7h0vqf8vkt52s
```

После выдачи `vpc.publicAdmin` группа при ближайшей же попытке (она повторяет раз в 5 минут) создала все три ВМ, и через полторы минуты они были `RUNNING_ACTUAL`. В таблице прав Compute Cloud для ВМ с публичным IP тоже указаны
`compute.editor` и `vpc.publicAdmin` ([документация](https://github.com/yandex-cloud/docs/blob/master/ru/compute/security/index.md)), но подтверждением для меня стал сам эксперимент.
Лог упавшего `apply`: [02_apply_failed.log](logs/02_apply_failed.log).

![apply: «Still creating…» и DeadlineExceeded](img/02_apply_failed.png)

**2. После таймаута группа не попала в state.** Провайдер отдал `DeadlineExceeded` на 30-й минуте, а группа в облаке осталась. Лечится
`terraform import yandex_compute_instance_group.lamp <id>`. Заодно выяснилось, что формат ID для роли —
`folder_id,роль,serviceAccount:id` **через запятые**, а не через `/`, как показывает `terraform state show`.

**3. К одной группе нельзя подключить NLB и ALB сразу, а `plan` этого не видит.** Я добавил блок `application_load_balancer` рядом с `load_balancer` и получил
после 8 минут создания ALB:

![apply: Only one of (load_balancer_spec, application_load_balancer_spec)](img/02b_apply_alb_failed.png)

К тому же провайдер помечает добавление этого блока как `forces replacement`: на группе «на лету» его не включить, она пересоздаётся.
Отсюда переменная `balancer` и `dynamic`-блоки. Лог: [02b_apply_alb_failed.log](logs/02b_apply_alb_failed.log).

**4. Новый NLB начал пропускать трафик не сразу, и я сначала неверно это объяснил.** После создания NLB цели были `HEALTHY`, а запросы на его адрес давали 0 из 8
примерно три минуты (создан 08:46:51, первые успешные запросы около 08:50). Я принял это за «плохой» публичный адрес (как в предыдущем ДЗ) и зря пересоздал NLB,
не дав ему времени. Позже тот же NLB с тем же адресом отвечал стабильно. Когда я потом вернул цели существующему NLB, он пропустил трафик за 5 секунд.
Вывод: задержка относится к только что созданному NLB, а не к адресу и не к подключению целей. Причину задержки не выяснил.

**5. Публичные IP части ВМ недоступны с моей машины.** Адрес `51.250.89.225` не отвечал по TCP 0 из 24 запросов, когда принадлежал `lamp-1`, и не отвечает теперь,
когда достался `lamp-3`. Через балансировщик те же ВМ отвечают. Значит, дело в маршруте до адреса, а не в ВМ. Изнутри облака я этого не проверял
(SSH на ВМ не открыт), так что это вывод по косвенным признакам.

**6. Измерения с моей машины имеют «дыры».** Гостевая ОС VirtualBox-машины замирает на 7–66 секунд (в системном журнале в эти моменты
`rtkit-daemon: The canary thread is apparently starving`, рядом работает MicroK8s), и поток запросов в это время не идёт. Что я с этим сделал:
скрипт пишет время каждого ответа и помечает паузы (`### пауза измерителя N с`), а обрывы, у которых время ответа больше `--max-time`, не относятся к балансировщику.
Первая версия скрипта подписывала обрыв именем ВМ из предыдущего успешного запроса (не очищала файл ответа); это исправлено, логи в репозитории сняты уже исправленной версией.

**7. `yandex_storage_object` не замечал смены файла.** Я перерисовал картинку, а `plan` не показал изменений: ресурс сравнивает только путь, а не содержимое.
Помог `source_hash = filemd5(...)` (после этого объект обновился на месте: 41 669 байт, ETag сменился).

**8. Роли в YC раздаются асинхронно**, поэтому между назначением ролей и созданием группы стоит `time_sleep` на 20 с. Назначать роли может только аккаунт с `admin`:
SA `terraform` получал его на время `apply` и затем терял. Состояние перед очисткой (до `destroy`):

## Ограничения

- **Одна зона и одна подсеть** (так в задании): при отказе ru-central1-a недоступно всё. ALB тоже размещён в одной зоне; для отказоустойчивости ему нужны подсети в нескольких.
- **NLB и ALB не работают одновременно** на одной группе (ограничение API); смена режима пересоздаёт ВМ.
- **Статистика тестов отказа скромная**: по одному прогону на балансировщик, один запрос в секунду, измерения с машины, которая сама периодически замирает.
  Окно обнаружения (секунды) на таком шаге видно как 1–2 обрыва; точнее я его не измерял.
- **У ВМ есть публичные IP** (по заданию они в public подсети) и открыт только 80/tcp; SSH нет, диагностика — через `yc compute instance get-serial-port-output`.
- **State локальный**, в нём лежит статический ключ `storage-sa`: `*.tfstate` и `personal.auto.tfvars` в `.gitignore`, в репозиторий не попадают.
- Бакет публичный осознанно (`read = true`); `list = false`.

## Очистка

```bash
cd terraform
export TF_CLI_CONFIG_FILE=$PWD/.terraformrc
# destroy тоже меняет роли, так что SA terraform снова нужен admin на время команды (см. «Как запустить»)
terraform destroy
```
